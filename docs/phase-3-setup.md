# Phase 3 Setup Guide — Advanced Retrieval (Hybrid Search)

This guide upgrades RAG from basic vector search to **hybrid retrieval**: dense (vector) + sparse (full-text) search, **parent-child chunking**, and **multi-query expansion**. The agent uses the new retriever automatically; no frontend changes are required.

---

## Prerequisites

- **Phase 2** must be complete: pgvector, `files`, `documents`, folder watcher, and agent running. You should have run `sql/supabase_phase2.sql` and optionally `sql/supabase_phase2_add_error_message.sql`.
- The same Supabase project and OpenAI key are used.

---

## Step 1: Run the Phase 3 SQL migration

1. In Supabase, open **SQL Editor** → **New query**.
2. Open **`sql/supabase_phase3.sql`** from this project and copy its full contents into the editor.
3. Click **Run** (or Ctrl+Enter). You should see “Success. No rows returned.”

This migration:

- Creates the **`parent_chunks`** table (id, content, metadata, file_id, chunk_index, created_at).
- Adds **`parent_id`** (FK to parent_chunks) and **`fts`** (tsvector for full-text search) to `documents`.
- Drops the IVFFlat index and creates an **HNSW** index on `documents.embedding`.
- Creates **GIN** indexes on `documents.fts` and `documents.metadata`.
- Defines **`hybrid_search(query_embedding, query_text, match_count, filter_file_id, rrf_k)`** for dense + sparse search with RRF and parent lookup.

---

## Step 2: Environment variables

No new required variables. Ensure `.env` still has:

- `OPENAI_API_KEY` (used for embeddings, chat, and query expansion).
- `DATABASE_URI` (Supabase Postgres).

---

## Step 3: Rebuild and run

From the project root:

```bash
docker compose up --build
```

The backend will use the new retriever and document processor. Existing files in `documents/` will be **re-processed** on next change or you can re-add them so they get **parent-child chunking** and appear in hybrid search.

---

## Step 4: Re-process existing documents (recommended)

After Phase 3, documents ingested in Phase 2 have no `parent_id` or `parent_chunks`. Hybrid search still works (it falls back to returning document content), but for best results:

1. **Option A:** Remove and re-add files: delete the files from the `documents/` folder, then copy them back. The watcher will process them again with parent-child chunking.
2. **Option B:** Touch files so the watcher re-processes: e.g. open and save, or run a script that updates the file timestamp. The watcher will detect the change and re-run the pipeline.

New files dropped into `documents/` are automatically processed with parent-child chunking (parents 2000 tokens, children 500 tokens).

---

## Step 5: Verify hybrid search

1. Open the **Chat** and ask a question that should be answered from your docs.
2. You should see the same flow (Retrieving… then streamed reply), but retrieval now uses:
   - **Dense** search (HNSW on embeddings).
   - **Sparse** search (GIN on `fts` with the query text).
   - **RRF** to combine dense and sparse rankings.
   - **Multi-query expansion**: the LLM generates 2 extra phrasings; all 3 are searched and results merged with RRF.
   - **Parent lookup**: matches are on child chunks; the context sent to the LLM is **parent** (larger) chunks for better coherence.

3. In **Documents**, existing files may show updated chunk counts after re-processing (child count is stored).

---

## How it works (brief)

- **Document processor** (`document_processor.py`): Splits each file into **parent** chunks (2000 tokens, 200 overlap), inserts them into `parent_chunks`, then splits each parent into **child** chunks (500 tokens, 50 overlap), embeds only children, and inserts them into `documents` with `parent_id`. The `fts` column is generated by Postgres from `content`.
- **Retriever** (`retriever.py`): Expands the user query to 3 variants via LLM; for each variant runs **hybrid_search** (dense + sparse, RRF in SQL); merges the 3 result lists with RRF in Python; returns top-k **parent** contents to the agent.
- **SQL** `hybrid_search`: Ranks **child** rows by dense (HNSW) and sparse (GIN) separately, applies RRF, aggregates score by parent, returns **parent** (or legacy document) content.

## Troubleshooting

| Issue | What to check |
|-------|----------------|
| **“function hybrid_search does not exist”** | Run `sql/supabase_phase3.sql` in the Supabase SQL Editor. Restart the backend. |
| **“relation parent_chunks does not exist”** | Same: run the Phase 3 migration. Re-processing will then create parent rows. |
| **Sparse search returns no results** | Sparse uses English `plainto_tsquery`. Very short or non-English queries may match little; dense search still runs. |
| **Query expansion is slow** | One extra LLM call per user message. To disable, call `retrieve(..., use_multi_query=False)` or add a config flag. |
| **HNSW build fails** | Some pgvector versions need at least one row in `documents` before creating HNSW. Process at least one file (Phase 2 or 3), then run the index creation part of the migration again. |
